# Требования MVP-1: публикатор и монитор

Версия 0.1 · 13.11.2026. Первая поставка: перенос публикации в облако и контроль сбоев (закрывает узкие места У3, У4).

## 1. User Stories

| ID | История | Критерии приёмки |
| --- | --- | --- |
| US-1 | Как автор канала, я хочу, чтобы одобренный пост выходил в назначенное время, чтобы канал не зависел от моего ПК | Given пост approved с scheduled_at = 19:05, When наступает 19:05 и ПК выключен, Then пост опубликован не позднее 19:10, статус published, сохранён tg_message_id |
| US-2 | Как автор, я хочу публиковать посты с фото | Пост с photo_file_id публикуется как фото с подписью; текст длиннее 1024 символов уходит отдельным сообщением |
| US-3 | Как автор, я не хочу, чтобы просроченные посты выходили пачкой после сбоя | Пост, просроченный более чем на 30 мин, не публикуется, получает статус overdue, автор получает уведомление. За один запуск публикуется не более 1 поста |
| US-4 | Как автор, я хочу знать, если пост не удалось опубликовать | До 3 попыток с интервалом 5 мин; после 3-й — статус failed, заполнен last_error, автору приходит уведомление |
| US-5 | Как автор, я хочу узнать о падении любого сценария | Сообщение в течение 5 мин: сценарий, узел, текст ошибки, ссылка на запуск |
| US-6 | Как автор, я хочу каждое утро видеть состояние канала | В 09:00 МСК сводка: опубликовано вчера, план на 3 дня, overdue и failed; предупреждение, если на 7 дней вперёд меньше 3 одобренных постов |
| US-7 | Как автор, я хочу проверить публикатор без риска для канала | В режиме test посты уходят в личку автору с пометкой [TEST]. Переключение в боевой режим — одно значение в БД |
| US-8 | Как автор, я хочу перенести текущую очередь из старой БД | Все посты загружены со статусом approved, время и текст совпадают, legacy_id сохранён |

## 2. Модель данных

См. [db/schema.sql](../../db/schema.sql).

- **posts** — очередь и история: тип, текст, фото, статус, время публикации, ID сообщения в канале, число попыток, последняя ошибка, ID из старой БД.
- **publish_log** — журнал каждой попытки публикации с результатом и режимом (test / live).
- **settings** — параметры: режим, канал, чат администратора, слоты, допустимое опоздание, лимит попыток.

Жизненный цикл поста:

```
draft → approved → publishing → published
publishing → approved (повтор, attempts < 3) → failed (attempts = 3)
approved → overdue (просрочен > 30 мин) → approved (после переноса автором)
любой статус до published → cancelled
```

## 3. Правила публикатора (каждые 5 мин)

1. Перевести в overdue все approved с scheduled_at раньше now() − 30 мин, уведомить автора.
2. Взять один пост: approved, scheduled_at ≤ now(), самый ранний; сразу перевести в publishing (`FOR UPDATE SKIP LOCKED` — защита от двойной публикации).
3. Отправить в канал (или в личку автору в режиме test).
4. Успех → published + tg_message_id; ошибка → attempts + 1, возврат в approved или failed. Каждая попытка пишется в publish_log.

## 4. Нефункциональные требования

- работа без ПК заказчика, 24/7;
- задержка публикации — не более 5 мин после scheduled_at;
- ни одна публикация не дублируется;
- токены и пароли хранятся только в Credentials n8n;
- время в БД в UTC, в сообщениях автору — МСК.
